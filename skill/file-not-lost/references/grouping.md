# 归组与命名

图好用不好用，八成取决于这一步：**同一份文件的 v1/v2/v3 必须合成一张卡**，拆成三张卡就是三张废卡。

## 同族判据

`scan_files.py` 先把文件名剥干净，再看剩下的是不是一样：

```
智能数据预测-核对数据抽屉-优化方案-v1-20261119.html
智能数据预测-核对数据抽屉-优化方案-v3-20261119.html
        ↓ 去掉 日期（20261119 / 2026-11-19）、版本（-v1）、尾巴（前 / 后）
        base = 智能数据预测-核对数据抽屉-优化方案
```

判定顺序：

1. **base 相同** → 同族，进一张卡的 `versions`
2. **base 不同但指向同一部件**（`核对数据抽屉` vs `核对抽屉`）→ 同族，你改 `name` 统一
3. **base 相同但其实是两个东西**（`结果卡片` 出现在两个需求里）→ 拆卡，`name` 里带上需求名
4. **拿不准** → 拆卡。拆错了顶多两张卡，合错了会把两份不同的文件说成同一份的版本，那是错的信息

脚本给你的是候选，不是结论。同族 > 1 的那几组过一眼再定。

## 什么进 versions，什么进 timeline

| | 进 `versions`（卡片的版本链） | 进 `days.snaps`（轨迹） |
| --- | --- | --- |
| 特征 | 有独立价值，会被再次打开 | 只是「改之前长什么样」 |
| 命名 | 有版本号或方案名 | 结尾 `-前` / `-之前` / 在 `迭代快照/` 里 |
| 数量 | 每卡 1–7 个 | 可以几十份 |
| 位置 | 卡片点开扇形 | 迭代轨迹区，默认收起 |

灰色地带：`优化方案-v3-20261119` 是版本还是快照？它有独立方案内容 → versions。
`设计稿-顶栏60px前` 只是上一秒的样子 → timeline。

## 命名建议（写给用户，不是硬约束）

```
项目名-部件名-稿型-日期[-版本].html

智能数据预测-核对数据抽屉-优化方案-20261119.html
智能数据预测-核对数据抽屉-优化方案-v2-20261119.html
智能数据预测-确认预测条件卡片-优化方案-20261119.html
```

好处很直接：`scan_files.py` 能自动分族、自动取日期、`name` 能自动截出「核对数据抽屉」。
名字乱的项目，归组就得全靠人工，几十分钟的事会变成几小时。

## 三步归组法

1. 跑 `scan_files.py`，看同族候选
2. 把**每个 base 对应到哪张卡、哪个区**列成一张表，让用户过一眼（这一步别自己拍）
3. 表确认后再写 `map.json`，`versions` 内严格按日期倒序

## 常见错法

| 错法 | 后果 |
| --- | --- |
| 每个文件一张卡 | 图变成文件清单，层叠 2 的价值全没了 |
| 按扩展名分组 | 设计师不按 HTML / PNG 找东西 |
| 把 37 份快照都做成卡 | 页面拉成几十屏，谁也不看 |
| 一个部件拆成「方案 A」「方案 B」两张卡 | 它们是同一张卡的两个版本，不是两个部件 |
| 同族里把旧版放 `versions[0]` | 主图、底栏、直达链接全指向旧版 |
