# 分类轴 · 产品经理（下一阶段）

`role: pm` 时用这一套。**卡片体系、层叠 2、扇形、删除撤回全部不动**，只换四个区的含义与卡片元信息。

设计师关心「我交付了什么、我在哪纠结过」；PM 关心「范围定没定、流程闭环没闭环、口径谁认、能不能验收」。所以同一份文件，在设计师图里是「核对数据抽屉方案」，在 PM 图里应该是「数据核对环节 · 待评审」。

## 01 需求与范围 · `type: lead`

**判据**：能回答「这次做什么、不做什么」的那份文件。通常是 PRD 或主需求文档。

`side` 四件套改写成：

| 字段 | PM 版写什么 |
| --- | --- |
| `title` | 这份需求的范围边界 |
| `body` | 本期包含 / 明确不包含 两块，用「；」分开 |
| `tags` | `已评审` `v3` `约稿 12 页` `依赖数据中台` |
| `path` | 同上 |

## 02 流程与状态 · `type: grid`

**判据**：讲「用户怎么走完这件事、走不通时怎么办」的稿子。一张卡 = 一个流程环节。

- 主流程、异常流、状态机、权限矩阵，各自成卡
- 每张卡的版本链放该环节的历次修订
- 卡片的 `status` 用评审态：`草稿` `评审中` `已确认` `已冻结`

## 03 方案对比与取舍 · `type: grid`

**判据**：同一问题有 2+ 解法、需要拍板的稿子。和设计师的 02 区看着像，差别在**结论**：

- 设计师图的 `note` 说「四版长什么样」
- PM 图的 `note` 必须说「选了哪个、为什么、代价是什么」

```json
"status": "已定 B",
"tone": "green",
"note": "选 B：一屏完成核对，代价是列宽不能自适应。"
```

拿不到结论就写 `status: 待决策` + `note` 写清卡在哪（缺数据 / 缺人 / 缺技术评估）。

## 04 验收与口径 · `type: subgroups`

**判据**：交付验收要用的东西。三组：

| 子组 | `id` | 装什么 |
| --- | --- | --- |
| 字段口径 | `g4a` | 字段字典、指标定义、数据源说明、样例数据 |
| 验收标准 | `g4b` | 验收清单、用例、埋点表 |
| 素材与会议 | `g4c` | 访谈记录、竞品截图、会议纪要、范围变更记录 |

## 卡片元信息（PM 版）

| 字段 | PM 版含义 | 例 |
| --- | --- | --- |
| `status` | 交付状态 | `评审中` `已确认` `待决策` `已冻结` |
| `tone` | 同上配色 | 已确认 `green`、评审中 `blue`、待决策 `orange`、草稿 `gray` |
| `unit` | 版本单位 | 默认 `个版本`，方案对比区可用 `份方案` |
| `note` | 一句话结论或卡点 | 「选 B：一屏完成核对」 |
| 版本 `note` | 这一版改了什么 | 「补异常流，去掉批量导入」 |

状态词表固定五个：`草稿` `评审中` `已确认` `待决策` `已冻结`。

## 不用做的三件事

1. **不要为 PM 版另建一套模板。** 差异全在数据里，`build_map.py` 不区分角色。
2. **不要在卡片里塞负责人、截止日期。** 底栏只放得下「名称 + 状态 + 日期体积」。真要追踪进度，那是项目管理工具的事，索引页的职责是让人找到文件。
3. **不要把会议纪要全部摊平。** 一个月的纪要是一张卡的多版本，不是三十张卡。

## 切换方式

`map.json` 里 `meta.role` 写 `pm`，然后按本文重排 `sections`。同一批文件可以在两份 map.json 里出现——一份给设计，一份给产品，各自演进，别互相覆盖。
